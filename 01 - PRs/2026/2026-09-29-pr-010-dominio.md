# PR #10 — feat(dominio): tipos, categorias e formatação de moeda e data

## 🎯 Contexto

Ordem 8 de [[2026-09-29-plano-da-v1-do-frontend]], a primeira do domínio. Antes das regras (cobrança,
alertas, redundância), o modelo precisa existir, e os testes precisam rodar no CI — a
[[ADR-001-frontend-primeiro-com-dados-locais]] manda as regras serem funções puras testadas com Vitest.

## 🔧 Mudanças

- `src/lib/domain/types.ts`: `Currency`, `BillingCycle`, `SubscriptionStatus`, `SubscriptionSource`,
  `IsoDate`, `Organization` e `Subscription` — o modelo da [[2026-09-29-especificacao-do-mvp]] em
  camelCase.
- `src/lib/domain/categories.ts`: a lista fechada de categorias, com o rótulo em português.
- `src/lib/domain/dates.ts`: `isIsoDate` (data sem hora que existe no calendário) e `toIsoDate` (o dia
  local de um instante — é assim que a tela calcula o "hoje").
- `src/lib/domain/format.ts`: `formatMoney` (Intl pt-BR), `formatDate` (`DD/MM/AAAA` direto na
  string) e os rótulos de ciclo, status e origem.
- Vitest 5 (`vitest.config.mts`), 20 testes em três arquivos, `npm test` e o passo de testes no CI
  (job renomeado para `lint · type-check · testes · build`).
- `@types/node` de 20 para 22: é a versão do Node local e do CI, e o Vitest 5 exige 22 ou mais.

## 🕵️ Dado sensível (LGPD e sigilo)

Nenhum. Os testes usam só valores fictícios.

## 🧠 Decisões técnicas

- **Categoria é lista fechada** (`communication`, `meetings`, `productivity`, `design`, `crm`,
  `marketing`, `development`, `finance`, `hr`, `storage`, `security`, `other`). A redundância compara
  categorias; com texto livre, "CRM" e "Vendas" esconderiam dois CRMs. "Reuniões e vídeo" é separada de
  "Comunicação" para o Zoom não virar duplicata do Slack.
- **`Organization` e `Subscription` só com os campos da especificação.** Moeda padrão, cotação,
  responsável e usuário entram nos PRs que os usam (cobrança, edição, sessão) — campo sem consumidor
  vira contrato que ninguém testa.
- **`IsoDate` é um apelido de `string`**, não um tipo marcado: a garantia vem da validação na escrita
  (repositório local, ordem 11), não do compilador.
- **Os testes rodam no fuso de São Paulo**, fixado no `vitest.config.mts`. Ver
  [[2026-09-29-teste-de-data-precisa-do-fuso-do-brasil]].
- `vitest.config.mts`, não `.ts`: o pacote é CommonJS, e o Vite avisa quando lê ESM num `.ts`. Mudar o
  `type` do pacote inteiro afetaria o resto do projeto.

## ⚠️ Armadilhas e aprendizados

- O `Intl` separa "R$" do número com **espaço não separável** (U+00A0), não com espaço comum. Teste que
  compara com `"R$ 8.450,00"` digitado falha.
- O `npm install` do Vitest 5 recusou o `@types/node` 20 (peer opcional `^22 || >=24`). A correção foi
  alinhar os tipos ao Node que roda, não `--legacy-peer-deps`.

## 🧪 Como testar

1. `npm test` — 20 testes. Com `TZ=UTC npm test` (como no CI), passam também. Sem a fixação do fuso,
   os dois testes de guarda falham — conferido.
2. `npm run lint && npm run type-check && npm run build`.

## 🚫 O que não foi verificado

- Nenhuma tela usa o domínio ainda.
- `formatDate` confia que recebe um `IsoDate` válido; quem garante é a validação na escrita.
